How it works

A walkthrough of the three pieces that make this site go: GitHub Pages, in-browser file rendering, and the encryption pipeline.

Stack

This is a static site — no server, no backend. The pieces:

  • Jekyll — the default static-site generator GitHub Pages ships with. Builds run on push.
  • Vanilla HTML + ES modules — no framework, no bundler. Two pages: index.html (the listing) and viewer.html (renders one file).
  • marked + DOMPurify (CDN) — parse and sanitize Markdown in the browser.
  • Web Crypto API + hash-wasm — AES-GCM decryption and Argon2id key derivation, all client-side.
  • Node CLI (tools/encrypt.mjs) — the only step that runs on your laptop. Takes plaintext from src/ and writes ciphertext to encrypted/.

1. How GitHub Pages loads this site

When you push to main, GitHub does roughly this:

  1. Spins up a build container.
  2. Reads _config.yml and runs Jekyll against the repo.
  3. Jekyll copies every file into a _site/ output directory, transforming any file whose top has YAML front matter. Files without front matter are passed through as-is.
  4. Publishes _site/ as a static website at the configured URL (here, ref.ezcoder.ink via the CNAME file).

Two important details for this project:

Front matter is what makes Jekyll touch a file.

index.html and viewer.html both start with:

---
layout: null
---

Those three lines are an empty front-matter block. They tell Jekyll: "process this file (so my Liquid template tags work), but don't wrap it in any layout." Without the block, Jekyll wouldn't expand {{ site.title }} or {% assign %} inside the file.

_config.yml controls what ships.

The exclude: list strips out things that shouldn't be on the public site: src/ (your plaintext source), tools/ (the Node CLI), node_modules/, README.md, Gemfile, etc. Importantly, encrypted/ is not excluded — GitHub Pages must serve the ciphertext blobs, public files, and manifest.json for the browser to fetch.

Several GitHub-Pages default plugins are also disabled in _config.yml (optional_front_matter, readme_index, default_layout, etc.) so that loose .md files in the repo are left untouched — we want them to remain as static files so the browser can fetch and render them.

2. How .md / .pdf / .html files are rendered

Markdown is the only format we need to do real work on. PDFs and HTML files are handed straight to the browser.

The index page

index.html renders the listing in two passes:

  1. Server-side (Jekyll) — the Liquid block on top walks site.static_files, finds every .md, .html, .htm, .pdf, groups them by top-level folder, and writes a <section> per topic. (This is the legacy plaintext-topic-folder route.)
  2. Client-side (JS) — the <script type="module"> at the bottom fetches /encrypted/manifest.json and hydrates a section per project, with a password form for any project marked "private": true.

Markdown → HTML

The index links to viewer.html?path=… for every .md file. The viewer:

  1. Reads the ?path= query parameter.
  2. fetch(path) to grab the raw Markdown text from GitHub Pages.
  3. marked.parse(md) turns the Markdown into an HTML string.
  4. DOMPurify.sanitize(html) strips anything dangerous (script tags, inline handlers, etc.) — defence in depth, since the source is yours but you might paste in untrusted content one day.
  5. Sets content.innerHTML = …. Done.

No front matter needed on your .md files — the viewer treats the whole file as Markdown body.

PDFs and HTML

For .pdf the index links straight to the file on GitHub Pages. The browser opens it with its built-in PDF viewer — no JS involved. Same idea for .html: it loads as a regular page.

For encrypted PDFs and HTML, decryption happens in memory, then the viewer wraps the resulting bytes in an iframe using URL.createObjectURL(new Blob([bytes], { type: '…' })). The blob URL only exists in this tab.

Encrypted HTML runs sandboxed.

The viewer's iframe for encrypted HTML sets sandbox="allow-same-origin" — no scripts, no top-navigation, no form submission. The HTML is yours, but the sandbox keeps "what if I encrypted a file someone sent me" from biting later.

3. How the encryption works

The threat model is simple: I want to put private notes in a public GitHub repo so I can read them from anywhere, but anyone scraping the repo should just see ciphertext.

Layout

Two parallel trees:

  • src/ — plaintext source. Gitignored. Never leaves your laptop.
  • encrypted/ — committed output. Contains manifest.json + per-project .enc blobs (or plain files for public projects).

Each top-level folder under src/ is a project with its own privacy decision: password = encrypted, or empty password = public.

The write side: tools/encrypt.mjs

Run from the repo root with npm run encrypt. For each project:

Private project
  1. Generate (or re-use) a random 16-byte salt — stored plaintext in manifest.json.
  2. Derive a 32-byte key with Argon2id (m=64 MB, t=3, p=1) from (password, salt). The password is never written anywhere.
  3. For each file: pick a random 12-byte IV, encrypt with AES-256-GCM, prepend [version=1][iv:12] → [ver][iv][ciphertext + 16-byte tag].
  4. Hash the resulting blob with SHA-256 and use the first 16 bytes as the filename (e.g. 4a1b16a2b865f74b4db570f0cf484a92.enc). The hash hides the original filename.
  5. Record an entry in manifest.json: { path, name, blob, type, ext, size }.
Public project

Copy bytes verbatim into encrypted/<project>/<subpath>. The manifest records a publicHref instead of a blob. No password prompt, no key, no IV.

The read side: crypto.js + the index/viewer

  1. Page loads. index.html fetches /encrypted/manifest.json.
  2. For each private project, it draws a password form. There's no list of files visible yet.
  3. You type the password. The script fetches the project's salt from the manifest, calls deriveKey(password, salt) → AES-GCM key.
  4. To verify the password is right, it fetches the first file's .enc blob and tries to decrypt. AES-GCM has built-in authentication: wrong key → the decrypt() call throws. Right key → you see the file list.
  5. The password is cached in sessionStorage for that tab only. Click a file → the viewer fetches that blob, decrypts it, renders it inline.

File format

Each .enc blob is just:

┌──────┬──────┬─────────────────────────────┐
│ ver  │ iv   │ ciphertext (incl. 16-byte    │
│  1B  │ 12B  │ AES-GCM auth tag at the end) │
└──────┴──────┴─────────────────────────────┘

Version byte gives us room to change the format later without breaking old blobs. Currently always 0x01.

What the manifest looks like

{
  "version": 2,
  "kdf": { "name": "argon2id", "memorySize": 65536, "iterations": 3, "parallelism": 1, "hashLength": 32 },
  "projects": [
    {
      "name": "personal",
      "private": true,
      "salt": "LzA5XrqFxC95kUxz4j6gTQ==",
      "files": [
        { "path": "personal/diary.md", "name": "diary.md", "blob": "personal/4a1b16a2b865….enc", "type": "md", "ext": "md", "size": 357 }
      ]
    },
    {
      "name": "public-notes",
      "private": false,
      "files": [
        { "path": "public-notes/getting-started.md", "name": "getting-started.md", "publicHref": "public-notes/getting-started.md", "type": "md", "ext": "md", "size": 698 }
      ]
    }
  ]
}

Everything in the manifest is plaintext: project names, file names, file sizes, salts. None of that is sensitive on its own. What's secret is the contents — and that's exactly what lives in the .enc blobs.

What this does and doesn't protect

What's protected
  • File contents of private projects. Without the password, the blobs are random-looking bytes.
  • Argon2id makes offline brute-force expensive (~64 MB / attempt, 3 iterations).
  • Wrong-password attempts are detected by AES-GCM's auth tag — no chance of silent corruption.
What's not
  • The existence of encrypted content, the project names, the number of files, and approximate file sizes are all public (they're in the manifest).
  • If your password is weak, leaked, or your device is compromised, the scheme can't help.
  • This is not a secure messaging system — there's no forward secrecy, no key rotation built in beyond "re-encrypt with a new password and force the old blobs to be deleted from encrypted/".
