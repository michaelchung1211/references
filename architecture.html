How this site works

Three moving parts work together: GitHub Pages hosts the files, the viewer renders them in the browser, and the encryption pipeline keeps private notes private. Read top-to-bottom for the full picture, or jump to a chapter.

3. Your browser

Reads. Decrypts in memory only.

Inside the encrypt step

password + salt (from manifest) → Argon2id  m=64MB · t=3 · p=1 → 32-byte AES key
plaintext file + random 12-byte IV + AES key → AES-256-GCM → [ver · iv · ciphertext+tag] = .enc

The browser does the inverse: password + salt → key, then key + .enc → plaintext. AES-GCM's auth tag means the wrong key throws an exception — no chance of silent corruption.

How the browser remembers your password

  1. Open the site. The index fetches /encrypted/manifest.json over HTTPS. Every private project shows a password form; file lists are hidden.
  2. Type the password. JS derives the key via Argon2id, then tries to decrypt the first blob to verify. Right key → cache sessionStorage["proj-pw:<project>"] and reveal the file list. Wrong key → "Wrong password"; nothing leaks.
  3. Stay in this tab. Cached password unlocks files instantly (no re-typing).
  4. Click Forget password. Removes just that project's entry from sessionStorage. Other unlocked projects stay open.
  5. Close the tab or refresh. The browser wipes sessionStorage. Every project is locked again on next visit.

GitHub Pages & Jekyll

What it solves: turning a git push into a live website with zero deploy commands.

The build pipeline

push to main GitHub spins up a build container Jekyll runs against the repo output to _site/ served at ref.ezcoder.ink

Step by step

  1. You push to main. GitHub detects a Pages-enabled repo and queues a build.
  2. A build container reads _config.yml. That file controls Jekyll: site title, what to exclude, which auto-plugins to disable.
  3. Jekyll walks every file. Any file whose first three lines are ---…--- (YAML front matter) gets processed: Liquid template tags like {{ site.title }} are expanded. Other files are passed through byte-for-byte.
  4. The result lands in _site/, which GitHub publishes as a static site.
  5. The CNAME file tells GitHub Pages to serve the site at the custom domain.

Why index.html and viewer.html start with three dashes

Open either file and you'll see this on top:

---
layout: null
---

That empty front-matter block is the magic. It tells Jekyll: "process me so my Liquid tags get expanded, but don't wrap me in any layout template." Without those three lines, {{ site.baseurl }} and friends would ship to the browser as literal text.

_config.yml controls what ships

The exclude: list strips out everything that shouldn't be on the public site: src/, tools/, node_modules/, README.md, Gemfile. Crucially, encrypted/ is not excluded — GitHub Pages must serve those .enc blobs and the manifest so the browser can fetch them.

Several Pages plugins are disabled on purpose

_config.yml explicitly turns off optional_front_matter, readme_index, default_layout, titles_from_headings, relative_links. If they were on, Jekyll would try to "help" by turning loose .md files into pages, which would prevent the viewer from fetching the raw text and would mangle anchors.

Where to look

  • _config.yml — site config, exclude list, disabled plugins.
  • CNAME — one line, the custom domain.

How files are rendered

What it solves: turning .md, .pdf, and .html files into something readable in the browser, without any build step per file.

Two pages cooperate:

  • index.html — lists every file (the homepage).
  • viewer.html — renders one file when you click on it.

The index: two passes over the same DOM

  1. Server-side (Jekyll) — the Liquid block on top walks site.static_files, picks out every .md / .html / .htm / .pdf, groups them by top-level folder, and writes one <section> per topic. This is the legacy plaintext-topic-folder path.
  2. Client-side (JavaScript) — the <script type="module"> at the bottom fetch()s /encrypted/manifest.json, then renders a section per project. Private projects get a password form; public projects get an immediate file list.

Markdown becomes HTML, in five lines

When you click a .md link, the index sends you to viewer.html?path=…. The viewer does this:

read ?path= fetch(path) marked.parse(md) DOMPurify.sanitize(html) content.innerHTML = …

Both libraries load from a CDN — the page itself is just glue.

No front matter required

The viewer treats the whole .md file as Markdown body. You don't need title: / date: blocks at the top of every note — just start writing.

PDFs and HTML

  • Public: the index links straight to the file. The browser's built-in viewer opens it — no JS involved.
  • Encrypted: the viewer decrypts the bytes in memory, wraps them in a Blob, and shows them in an iframe via URL.createObjectURL(). The blob URL only exists in your tab.
Encrypted HTML runs sandboxed

The iframe for decrypted HTML carries sandbox="allow-same-origin" — no scripts, no top-navigation, no form submission. The HTML is yours, but the sandbox keeps "what if I encrypted something untrusted" from biting later.

Where to look

  • index.html — both passes live here.
  • viewer.html — the per-file renderer.

The encryption pipeline

What it solves: putting private notes in a public GitHub repo so I can read them from anywhere, while anyone else who finds the repo sees only ciphertext.

Two parallel trees

  • src/ — plaintext source. Gitignored. Never leaves your laptop.
  • encrypted/ — committed output. Contains manifest.json + per-project .enc blobs (or plain files for public projects).

Each top-level folder under src/ is a project, and each project independently chooses its own privacy: password = encrypted, or empty password = public.

Building a key from a password

You never store the key. You store only the salt. The key is re-derived every time, from your password + the salt:

password + 16-byte salt Argon2id
m=64MB, t=3, p=1 32-byte AES key

Argon2id is a deliberately slow, memory-hungry function. Even with a fast GPU, brute-forcing one password takes ~64 MB of RAM and three iterations per attempt — far slower than plain SHA-256.

The .enc blob format

Every encrypted file on disk has the same shape:

version
1 byte
always 0x01
IV
12 bytes
random per file
AES-GCM ciphertext + auth tag
n + 16 bytes
the last 16 bytes are the integrity tag

The whole blob is hashed with SHA-256; the first 16 bytes of the hash become the filename, e.g. 4a1b16a2b865f74b4db570f0cf484a92.enc. This hides the original filename — the manifest is the only place that maps a blob back to its real name.

Write side: tools/encrypt.mjs

Run from the repo root. Per-project: you pick which projects to (re-)encrypt; the rest are left untouched.

  1. The CLI walks src/, groups files by top-level folder, and asks you which projects to operate on.
  2. For each selected existing private project: it asks for the password and verifies it by decrypting one existing blob. If you typo, nothing is wiped; you just get another try.
  3. For each selected new project: it asks for a password (empty = public). If you choose a password, a random 16-byte salt is generated.
  4. For each selected project: it wipes encrypted/<project>/, then either encrypts every file with AES-GCM (private) or copies bytes verbatim (public).
  5. The manifest is rewritten with new entries for selected projects + previous entries for skipped ones.
  6. Any encrypted/<project>/ whose src/<project>/ has been deleted is garbage-collected.

Read side: crypto.js + the index/viewer

  1. The page loads. index.html fetches /encrypted/manifest.json — project names, salts, file sizes are all visible.
  2. For each private project the index draws a password form. The file list is hidden.
  3. You type the password. The JS calls deriveKey(password, salt), then fetches the project's first blob and tries to decrypt it.
  4. AES-GCM is authenticated: the wrong key throws an exception. Right key → file list reveals. Wrong key → "Wrong password" message; nothing leaks.
  5. The password is cached in sessionStorage under proj-pw:<project> for that tab only. Click a file → the viewer re-derives the key and decrypts in memory.
  6. A Forget password button appears once a project is unlocked. Clicking it removes that one project's entry from sessionStorage and re-shows the password form. Other unlocked projects stay open.

What the manifest looks like

{
  "version": 2,
  "kdf": { "name": "argon2id", "memorySize": 65536, "iterations": 3, "parallelism": 1, "hashLength": 32 },
  "projects": [
    {
      "name": "personal",
      "private": true,
      "salt": "LzA5XrqFxC95kUxz4j6gTQ==",
      "files": [
        { "path": "personal/diary.md", "name": "diary.md", "blob": "personal/4a1b16a2b865….enc", "type": "md", "ext": "md", "size": 357 }
      ]
    },
    {
      "name": "public-notes",
      "private": false,
      "files": [
        { "path": "public-notes/getting-started.md", "name": "getting-started.md", "publicHref": "public-notes/getting-started.md", "type": "md", "ext": "md", "size": 698 }
      ]
    }
  ]
}

Everything in the manifest is plaintext: project names, file names, file sizes, the salt. None of that is sensitive on its own. What's secret is the contents — and those live inside the .enc blobs.

Threat model

What's protected
  • The contents of private files. Without the password, blobs are random-looking bytes.
  • Argon2id makes offline brute-forcing expensive (~64 MB and 3 iterations per attempt).
  • Wrong-password attempts are detected by AES-GCM's auth tag — no silent corruption.
  • Re-encrypt typos are caught before any data is wiped (see chapter 3 step 2).
What's not protected
  • The existence of encrypted content, the project names, file counts, and approximate file sizes are public (they're in the manifest).
  • If your password is weak, leaked, or your device is compromised, the scheme can't help.
  • There's no forward secrecy — the same password derives the same key forever.

Where to look

  • tools/encrypt.mjs — the CLI.
  • crypto.js — the browser-side helpers (mirror of the CLI's crypto).

FAQ & recipes

Common operations and what happens under the hood.

How do I delete a single file?

  1. Delete the file from src/<project>/<file>.
  2. Run npm run encrypt -- <project> — you have to select that project, otherwise the CLI leaves it alone.
  3. The CLI wipes encrypted/<project>/ and rewrites it without the deleted file. The manifest entry is replaced.

Every other file in that project gets re-encrypted with new IVs, so the git diff for that project will include all of its blobs even though only one file changed. That's expected.

How do I delete an entire project?

  1. Delete the whole src/<project>/ folder.
  2. Run npm run encrypt (any invocation works — even encrypting an unrelated project).
  3. The garbage-collect step at the end of the CLI removes encrypted/<project>/, and the manifest is rewritten without that project's entry.

Can manifest.json get corrupted if I do something wrong?

In normal use, no. The CLI rewrites the manifest atomically at the end of a run; if it crashes earlier, the manifest is untouched. The two real risk paths:

Wrong password during re-encrypt

Previously this was a footgun. Now the CLI verifies your password against an existing blob before wiping anything. Typo → "Wrong password — try again. (Nothing has been written yet.)" Your old blobs are safe.

Manually editing manifest.json

Possible but discouraged. As long as the JSON stays valid and each entry keeps its fields (name, private, files[], salt for private), the site keeps working. If you break it, the cleanest fix is to delete the manifest entry + the corresponding encrypted/<project>/ folder and re-run encrypt.

I forgot the password to a project. Can I recover the files?

No. That's the point of Argon2id + AES-GCM. The plaintext is gone from encrypted/ entirely. If you still have your src/ folder on disk, it's plaintext and you can start a new project with a new password.

To start fresh: delete the project's entry from encrypted/manifest.json, delete encrypted/<project>/, then run npm run encrypt -- <project> — the CLI will treat it as new and ask for a new password.

How do I change a project's password?

Delete the project's entry from encrypted/manifest.json, delete encrypted/<project>/, then run npm run encrypt -- <project>. The CLI treats it as a new project (since there's no prior entry) and prompts for a fresh password.

How do I flip a project between public and private?

Private → public: edit encrypted/manifest.json, set "private": false, delete the project's .enc blobs, then re-run encrypt. (Or just delete the project's entry entirely and let the CLI re-prompt.)

Public → private: delete the project's entry from encrypted/manifest.json and re-run; the CLI will prompt for a password.

How do I lock a project again without closing the tab?

Click the Forget password button that appears under each unlocked private project's file list. It removes that project's entry from sessionStorage and re-shows the password form. Other unlocked projects stay open. The button is only visible while the project is unlocked.

Closing the tab or doing a full refresh has the same effect for every unlocked project at once.

How do I get a PDF of the system diagram?

Open /diagram.html and click the Save as PDF button (or press Cmd/Ctrl + P). The page is print-optimized for landscape A4 and the browser's print-to-PDF produces the file.

There's no pre-baked PDF artifact in the repo on purpose — the diagram stays in sync with the code that way. If you want one committed, install Puppeteer / Chrome and run chrome --headless --print-to-pdf=diagram.pdf file://$(pwd)/diagram.html.

What if I clone the repo on a different laptop?

The clone has encrypted/ but not src/ (which is gitignored). You can view the site as a reader — type your password and read files — but you can't add new content until you also clone your local src/ over by hand (or copy files in fresh). The encryption pipeline doesn't try to round-trip through git.
